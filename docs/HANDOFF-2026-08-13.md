## COS north star

COS is the intelligence/governance/memory system, not Qwen, GPT, Claude, Gemini, RunPod or any other provider. The buyer must be able to bring its own model/provider/agent runtime. SignalBoost intelligence must survive an underlying model swap.

The target is workload-relative independent capability, not self-reported confidence:

- mature target: roughly 85% independent pass rate on the defined SignalBoost workload;
- longer-term ambition: roughly 92–95% only if held-out evidence supports it;
- external frontier models handle the difficult/novel/disputed/high-consequence tail.

Do not lower the 0.72 default COS gate or inflate confidence merely to improve the independence percentage.

## 3. Answer quality, cache and provenance hardening

The COS answer path now distinguishes answer reuse, factual evidence, user memory and procedural skills.

Authoritative evidence semantics:

`retrieved → relevant → selected → injected → cited`

A component is `USED` only when the answer demonstrably cites/uses it. Retrieval/injection alone is not use.

Key work:

- answer-cache policy versioning and bounded age prevent old answers from surviving model/prompt/gate changes indefinitely;
- cache-origin provenance is separated from current-request execution telemetry;
- unused KG/corpus rows do not raise the evidence confidence ceiling;
- procedural `[SK#]` guidance is tracked separately from factual `[KG#]/[CL#]/[EM#]` evidence;
- the model-only ceiling remains 0.78, above the default 0.72 gate;
- generic diagnostic answers are capped/repaired rather than rewarded for vague category names.

PR #1158 added citation-safe procedural skill provenance. If a validated skill was injected but the local model omitted its `[SK#]` tag, COS may make one citation-only repair pass. The repair is accepted only if:

- every added skill tag is one supplied to the model;
- removing the tags leaves the original answer substance unchanged.

Runtime telemetry from the production proof recorded:

- `[cos-skill-citation-repair] attempted:true`;
- `accepted:true`;
- allowed/cited tag `[SK1]`.

The first verifier run correctly exposed that a pre-#1158 cached answer bypassed the new citation contract. `COS_ANSWER_GATE_REVISION` was therefore bumped so older answers written under the previous citation/accounting policy became unreachable rather than being deleted or silently reused.

Temporary benchmark/verifier routes used during proof were deleted. Production was explicitly checked to return 404 for the verifier after cleanup.

## 6. Durable cognitive lifecycle

The explicit lifecycle now exists in production code/schema:

`encountered → evaluated → understood → practiced → validated → learned → mastered`

Memory types are kept conceptually separate:

- episodic experiences;
- semantic/factual memory;
- procedural skills;
- metacognitive weakness/strength state;
- future consolidation/reconsolidation/forgetting.

Only `validated`, `learned` and `mastered` procedural skills are eligible for live COS retrieval. Lifecycle state is capability evidence, not an automatic confidence bonus.

## 8. Qwen3 model upgrade — exact limitation

Current live production reasoner remains `qwen2.5-coder:32b`.

The repository bootstrap/default was changed to `qwen3:30b` so future/restarted intended installs do not silently return to the old coder default. However, the existing running pod still needs the Qwen3 model pulled and the served model switched.

Attempts to preload the ~19 GB model through the existing RunPod HTTPS/Ollama gateway failed because the gateway/proxy buffers the upstream response and long pulls exceed the request path timeout. Streaming from Ollama does not solve this when the intermediate gateway buffers the stream. RunPod's management API does not expose arbitrary remote shell execution.

Therefore the remaining cutover requires one of:

- RunPod Web Terminal, or
- SSH/another legitimate pod shell mechanism.

After installation, verify before changing claims:

1. `ollama list` contains the intended Qwen3 model;
2. direct authenticated inference succeeds;
3. `LOCAL_AI_MODEL` points at it;
4. `/api/cos-primary/health` or equivalent production health reports the new model;
5. rerun a held-out benchmark suite and compare quality/latency/cost rather than assuming the newer model is better.

Do not expose `/workspace/cos-api-key` or ask the user to paste it into chat/GitHub.

## 10. Self-Healing Supervisor — proactive monitoring and closed loop

Native proactive monitoring was already production-runtime-verified before this handoff:

- API p95 latency/5xx probes;
- database latency/connection pressure;
- storage reachability/usage/capacity when quota is configured;
- TLS certificate-expiry checks;
- Vercel/provider observations;
- SignalBoost platform-health observations;
- durable samples in `self_healing_native_probe_samples`;
- scheduled 15-minute production cron.

PR #1159 merged as `aadb940d9074c9ed19c7913b5cbea83eae37811e` and closes the important architectural gap where monitoring could detect an anomaly but stop at the HTTP response.

The native loop is now:

`native anomaly → bounded Portable Connector evidence → COS-first diagnosis → registered repair plan → Agent Gateway/MCP governance → execute if permitted / stage or require approval if not → verify/audit`

Canonical file: `saas/self-healing-host/native-autonomous-loop.ts`.

The cron only enters the expensive diagnostic/remediation path when incidents exist. It remains `CRON_SECRET` protected and fails closed if the native probe store is unavailable.

PR #1159 adds **no new mutation authority**. Unknown/consequential actions remain fail-closed/approval-gated. The purpose is to connect detection to the same governed action boundary a buyer receives, not to make COS an unrestricted administrator.

See `docs/portables/self-healing-monitoring-current-state-20260813.md`.

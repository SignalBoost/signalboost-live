## COS cache / provenance / learning state

The semantic cache is now proven working end-to-end in production. The repeated multi-tenant SaaS benchmark produced authoritative provenance showing `Semantic Cache: USED — 1 cached result contributed`, `Local Reasoning Engine: NOT INVOKED`, `External AI Provider: NOT INVOKED`, and confidence `0.85`. This is the acceptance behavior: a repeated high-confidence answer can bypass both Qwen generation and external AI.

The cache failure was traced to embedding/schema problems. The local embedding path uses `nomic-embed-text` with 768-dimensional vectors; the corrected semantic-cache migration and RunPod embedding-model self-heal path are now part of the codebase. Do not regress the cache to a 1536-dimensional schema.

Authoritative provenance is also functioning: it reports actual server execution telemetry rather than model-generated reconstruction and distinguishes retrieved evidence from evidence actually cited/used.

Autonomous learning has **not stopped**. Recent learning runs acquired external documents and at least one item passed admission (`accepted: 1`). The remaining issue is knowledge utilization, not total acquisition failure. Source adapters still showed intermittent Crossref/GDELT/YouTube/OpenAlex errors during learning runs, so source reliability remains a follow-up hardening area.

The live answer path currently retrieves Continuous Learning material successfully, but Enterprise Memory / Knowledge Graph contribution has been weak because structured facts were not being promoted automatically and retrieval remains primarily lexical in `cosFirstAnswer.ts`.

PR #1128 (`f862ebe7`) is merged and closes the first promotion gap: learned corpus documents are automatically passed through the existing local-only grounded fact extractor and written into `cos_knowledge_facts`. The final implementation moved promotion into a dedicated `/api/cron/cos-knowledge-promotion` cron, queries genuinely unprocessed rows instead of a fixed newest-200 window, durably records extraction completion even when a document yields zero facts, and reports all-failed extraction batches as errors instead of success.

Important deployment/database follow-up: verify that `saas/supabase/migrations/20260813_cos_learning_fact_promotion_state.sql` has been applied to the production Supabase schema before expecting the dedicated promotion cron to work. A green Vercel deployment does not prove a database migration was applied.

A previous grounding-enforcement experiment (#1126) reduced a valid benchmark from 0.85 to 0.65 by applying a punitive citation/confidence rule. It was deliberately rolled back in #1127. Do **not** reintroduce blanket penalties such as “retrieved > 0 and cited = 0 => confidence below threshold.” Retrieved evidence may be irrelevant. Grounding must be relevance-aware.

### Next COS sequence

1. Verify the promotion-state migration in production, run/observe `/api/cron/cos-knowledge-promotion`, and confirm `cos_knowledge_facts` begins growing from accepted learned documents.
2. Add 768-dimensional embeddings to structured knowledge facts and implement semantic KG/Enterprise Memory retrieval instead of relying on `ILIKE` term matching.
3. Add pipeline telemetry that distinguishes `retrieved → relevant → selected/injected → cited/used` per system. A `0 cited / 12 retrieved` result is only a failure when relevant evidence actually existed.

5. Then tune grounding quality. Confidence should only be affected when genuinely relevant evidence was available and the answer ignored it.

## Self-Healing Supervisor monitoring correction

The product should be described as proactive and monitor-capable, not merely reactive to alerts from another product. Native monitoring is default-capable; buyer monitoring may coexist in hybrid mode or replace it by explicit buyer choice.

Existing external monitoring adapters: Datadog, PagerDuty, AWS CloudWatch/EventBridge, Prometheus Alertmanager, Splunk, Azure Monitor, Grafana Alerting and Google Cloud Operations. They remain `staged`, not `certified`, pending real-provider evidence.

Next native monitoring work: real API latency/5xx, database, storage, and TLS/certificate-expiry probes. The branch `feat/native-proactive-monitors-20260812` exists, but attempted writes were blocked; do not assume those probes exist.

Detailed handoff: `docs/portables/self-healing-monitoring-current-state-20260812.md`.

## Safety/automation doctrine

Routine remediation may be automatic only when it is explicitly registered and pre-authorized within bounded capability/resource/method/parameter/reversibility/execution limits. Consequential, destructive, financial, credential/security, and otherwise approval-required operations continue through the signed approval path. Monitoring itself is observation-only and does not create mutation authority.
